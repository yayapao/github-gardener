# README、项目推广与个人主页

## 先理解项目

读取目标分支 README、入口/API、示例、Release 与相关 Issue。把候选文案对应到事实：功能在哪里实现、解决谁的哪个问题、最小用例是什么、有哪些已知限制。

若现有 description 不清楚，写 2–3 个有侧重的短候选并给理由。Topics 选真实用途、领域和技术，不为所有项目默认追加 developer-tools。Homepage 指向实际可用的演示或文档。

## 项目 README

保留准确内容，按项目需要调整：

- 开头一句说明适用人群、具体结果和核心边界。
- 最小可用示例给真实命令、输入与预期输出；未经执行明确说明验证范围。
- 演示图来自仓库可用资产；不得编造截图、性能、用户量、推荐语。
- 安装、运行时版本与 Release 一致。
- 把必要配置和安全边界放在使用者做决定的位置。
- 贡献方式、支持渠道、License 遵从项目现有约定；许可证由权利人决定。

文件组织依项目而定；Profile/文档项目不套用代码工具的安装模板。把内容改动控制在能审阅的 diff，避免无必要重写。

## Profile

设计、项目编排、视觉素材与篇幅控制统一见 [Profile 设计与编排](profile-design.md)。脚本候选只是起点，不能按 Star 或健康分直接决定展示顺序；展示项目也不等于承诺持续维护。

## 审阅交付

交付候选 README、description/Topics 前后值、变更理由、事实来源和 diff。内容待确认之处明确标出。文档 PR 与仓库设置分开授权，按 safe-change-workflow.md 执行。

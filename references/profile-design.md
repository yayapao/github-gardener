# GitHub Profile 设计与编排

目标：让访客快速理解“你在做什么、哪些作品值得看、从哪里开始”。先形成可审阅的内容和视觉，再按授权发布；不要把个人主页写成仓库审计报告。

## 定位与证据

- 优先采用用户本次明确的方向、受众和语言；已有 Profile、Bio、置顶项目帮助理解风格。缺少信息时先沿用现有介绍出草案，只在缺口影响设计时提问。不把本次用户的 Agent 方向写死为所有人的定位。
- 读取范围内的 OWNER/OWNER 及其实际默认分支。列表未命中不等于不存在；403、限流或部分 GraphQL 错误不能当 404。只有明确 NOT_FOUND/404 且账号和范围正确时，才准备新建方案。
- 按用户目标选少量互补作品，默认约三个。技术工具、产品起点、具体场景可以互补，但不强制套这三类。解释本次排序；Star 和健康分提供背景，不能代替代表性判断。
- 从候选仓库的 README、真实入口/示例或 Release 核对介绍；留下本地来源。只推荐范围内公开、未退役且适合展示的项目，复查直接链接对应的文件。成熟而安静的工具也可能适合展示，不能把它包装成正在活跃开发。
- 公开仓库可能链接私有或内部文档：每个对外入口仍需核验可公开访问，不能因为当前 gh 登录态能读就判为公开。公开页面不得带出私有项目名、内部主机、审计数据、私人联系方式或未经证实的用户量、职业头衔和成果。

用户要求参考案例时，实时查看少量有代表性的 Profile 及同名仓库，给出直接链接、值得借鉴之处与适用场景；从信息结构、个人表达或作品入口提炼设计，不照搬别人的身份和素材。已有方向足够明确时，直接设计，不额外扩展为案例研究。

## 内容编排

先做一个简洁版本，通常包含：

1. **一句定位**：具体做什么，让谁得到什么结果；保留用户已有的自然表达。
2. **精选作品**：项目链接、一个具体用途、必要时一个入门文档入口。每个项目通常一两句，不重复放同一个“Explore”链接。
3. **少量个人信息**：简短当前关注点、技术栈或用户提供的联系渠道，按需要取舍。

首屏先放定位和最相关作品。短页面通常无需目录；避免在介绍、研究方向和页尾重复同一套口号。语言服务于受众，沿用用户选择；需要双语时用一句补充，不逐段机械翻译。原有准确内容与用户个性应保留，不必为了套模板重写全部内容。

使用 GitHub 支持的 Markdown 和轻量 HTML。项目说明保留为可搜索、可复制的文本；固定宽度表格、把文字做成图片的项目卡片容易影响手机阅读。长表格、徽章墙、动态统计和最近更新栏目只在有明确价值、可靠数据源和维护方式时使用；不要默认增加自动化。

## 视觉素材

横幅是可选项。根据用户风格选择克制的配色、清晰标题和一个能表达工作方向的视觉元素；素材应原创或来自允许使用的用户资产。不要把某次的“深色 + 薄荷绿”固定为所有主页的模板。

适合简单横幅时，直接制作仓库内的静态 SVG，并用相对路径引用：

```html
<p align="center">
  <img src="./assets/profile-banner.svg" width="100%" alt="准确描述标题和画面用途" />
</p>
```

SVG 提供 viewBox、title/desc，使用系统字体、基础图形和适量文字。避免脚本、foreignObject、外部图片/字体和追踪资源。手机上横幅会整体缩小，小字只能作为装饰；核心定位和项目用途仍放在正文。需要复杂插画时可使用当前可用的图像工具，但不强制新增依赖。

## 编辑与精简

用户说“太长，减少 50%”时，修改主页候选本身，同时更新预览、diff 和文件哈希。先合并重复定位、删除低优先栏目和重复入口，再把每个项目收为一句用途；保留项目链接和用户明确要求的重点。

按可见文案比较同语言版本的篇幅：英文按词、中文按字，同一指标前后一致；约减半可接受目标篇幅的少量浮动。Markdown URL、空行和 SVG 源码不应充当文字量。只把字节数作为辅助，不能用删空行或加链接伪装完成。若用户必须保留的内容与目标冲突，先交付最接近要求的版本并说明取舍。

## 预览与验证

准备 current/、proposed/，素材放在 proposed/assets/。用 GitHub Markdown API 校验渲染；请求体从 JSON 文件读取，避免 shell 插值。POST /markdown 仅渲染内容，不创建仓库或提交。新仓库尚不存在时，不传不存在的 repository context。

```bash
gh api --method POST markdown --input render-request.json > rendered-readme.html
```

render-request.json 的 text 是候选 README 全文，mode 使用 gfm。组装本地预览时，将相对素材路径映射到真实文件位置；这种改写只用于预览，不能污染发布的 README。

有浏览器时检查实际页面：横幅加载、文字层级、项目链接和内部锚点；关注桌面及窄屏（例如 390px、320px）溢出与可见性，以及深浅色可读性。保存可复核截图。没运行浏览器或 GitHub 渲染时明确未验证项，不把本地 HTML 模拟成已发布效果。

交付应简洁：预览、README、完整 diff、验证结果和待批准的精确动作。原始来源、内部分析、预览 HTML 和截图留在本地，除非用户要求，不放入 Profile 仓库。

## 新建与发布

存在同名仓库时，按 [安全变更流程](safe-change-workflow.md) 读取真实基准 SHA 并准备文档 PR。尚不存在时，用空的 current/ 和专用模式生成添加两个文件的方案；没有横幅就省略相应 --file：

```bash
python3 scripts/prepare_change.py plan --repo OWNER/OWNER --new-profile \
  --current-dir ./current --proposed-dir ./proposed \
  --file README.md --file assets/profile-banner.svg --output ./change
```

此模式只记录 baseSha=null、expectedRepositoryState=absent 和 visibility=public，不联网验证，也不代表创建已授权。展示新建公开同名仓库及分支/PR 的具体动作，取得对应授权后才创建；初始化后读取真实 HEAD，重新生成基于该提交的差异，确认候选字节仍与用户已审阅版本一致。若出现他人新内容或实质变化，重新展示，不能用旧授权覆盖。

“创建 PR”不包含合并。用户审阅具体候选后明确要求“请发布/上线主页”，可执行使该版本上线所必要的创建、提交、PR 和合并；保留精确 HEAD、合并方式与核验记录，沿用授权，不在每个必要步骤重复询问。若目标或内容不清楚，先澄清。Bio、Topics、Homepage、置顶或其他仓库变更不混入文档发布。

合并后核对默认分支文件哈希，再打开公开账号主页检查实际渲染、素材和入口；交付主页与 PR 链接及真实状态。远程文件已合并但页面暂未更新时，区分这两个事实，不能提前声称视觉验收通过。
